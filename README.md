## 三个最该被复用的 schema

1. **stay/go 矩阵行**：`库(★/lic) | ①可复跑②量化③调用证据 | 处置 | 一句话依据`——处置列可被脚本解析 Counter 回填报告头部；矩阵还须与权威元数据池做**行级 diff**（防幻影行/漏库，见 R7-a）。
2. **复审 gold**（`eval/*.jsonl`）：类型化问题（`noul|choice|score`）× `probabilities` 求和 1±0.02 × 5 samples × 倒序盲判 `blind:agree` × `rationale` 必填 × `note` 必含样本来源声明——全部可机检（任意 JSONL 校验器可参照实现）。
3. **存在性验证协议**（`verify_existence_v3.py`）：jsDelivr 主通道 + API 备援 + **正负对照**；对照组不过关 → 整批结果作废。这条是 266→259 翻案案的产物。

## 如何复现"你的 266→259"（onboarding）

1. 从多个 awesome 目录抽取 repo 行 → 仿 `build_inventory.py` 的正则分类器归批（版本写进 CSV 头部，删改留注释根因）；
2. 跑 `verify_existence_v3.py`——**先放正对照**（已知存在的库）**和负对照**（已知不存在的名字），两对照不同时过，任何"存在/不存在"结论都不采信。我们就这样发现旧代理对任意 URL 回 200，把"266 全存在"翻案成 259（7 库不存在）；
3. 每批报告写完后跑 `_rbN_precheck.py`（处置 Counter + `header ok==POOL` 硬门 + token→源文件反查 + 体积走 `getsize`），**先脚本后文档**，头部统计从脚本输出回填。

全部脚本以仓库根为工作目录运行（Python 3.12，无第三方依赖）。快照目录 `_bN/` 未随仓发布（第三方 README 版权归原仓库），用 `b2_fetch.py`/`b2_meta.py` 按清单自行重建。
